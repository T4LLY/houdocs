### [Fixed] C1. Search rows are committed before embeddings are computed; a failed embedding run leaves entries permanently skipped from the dense index

- **Severity:** High
- **Confidence:** High-confidence
- **Affected file/symbol:** `src/houdocs/search/hybrid.py` — `HybridSearchBackend.upsert` (commit at line 110, embedding/vector upsert at lines 120–129); `src/houdocs/search/index.py` — `SearchIndexer.index_all` change detection via `entry_states`.
- **Description:** `upsert()` first writes `search_entries`/`search_content`/`search_fts` rows and commits (hybrid.py:110), recording `content_hash` and `embedding_profile_id`. Only afterwards does it call `_ensure_vector_cache(...)` and `dense.upsert(...)` (hybrid.py:124–129). If the embedding provider raises (`embedding_failed` / `embedding_model_load_failed` are `HouDocsError`s), the already-committed rows keep `is_current = 1` with the current `(hash, profile)` tuple. On the next `houdocs init`, `SearchIndexer.index_all` treats a section as needing work only when `entry_states[id] != (hash, profile)` — so those entries are skipped and their vec0 rows are never created.
- **Why it matters:** The failure mode is silent and permanent: lexical search keeps working, but the dense half of the hybrid search silently degrades for exactly the documents that were mid-flight when the embedding error occurred, and re-running `init` does not heal it. Users have no signal other than subtly worse recall.
- **Evidence:** hybrid.py:110 `connection.commit()` inside the entry-write block precedes hybrid.py:124–129 `_ensure_vector_cache` / `self.dense.upsert`. index.py computes `changed` by comparing `existing.get(section_id)` (from `entry_states`, hybrid.py:149–165, which reads `content_hash, embedding_profile_id` of `is_current=1` rows) against the new `(hash, profile)` tuple. `tests/test_search.py::test_search_reuses_unchanged_entries_and_reindexes_profile_change` asserts the skip behavior that makes this permanent.
- **Expected impact:** After any aborted init (embedding model download failure, OOM, Ctrl-C at the wrong moment), a subset of sections permanently lacks dense vectors until their content changes or the search DB is deleted manually.
- **Trigger conditions:** Embedding failure (or process kill) after at least one per-document `upsert` has committed its entry rows but before `dense.upsert` for those entries completes.
- **Suggested verification:** In a scratch `search.db`: insert entries via `upsert` with an embedding provider whose `encode` raises on the second call; re-run `SearchIndexer.index_all` with a working provider; assert whether the failed entries gain vec0 rows (they will not). Then assert a fix (e.g., recording a "vectors_persisted" flag per entry, or upserting vectors before committing entries, or including a dense-coverage check in the skip condition) heals them.

#### Update — 2026-09-07 09:44 — Base 76b1305

Verified by control flow and regression test: persisted `search_entries` state previously preceded embedding and dense writes, so the unchanged-state check skipped a failed entry. `HybridSearchBackend.upsert()` now creates and persists dense vectors before publishing lexical/entry rows. A failed embedding leaves no current entry state, and `test_search_retries_entries_after_embedding_failure` verifies a subsequent successful init indexes the entry. Result: Fixed.

### [Fixed] C2. `NodeRepository.resolve()` ignores the computed document priority and orders by the hash column — duplicate canonical node types are resolved arbitrarily

- **Severity:** Medium
- **Confidence:** High-confidence
- **Affected file/symbol:** `src/houdocs/node/repository.py` — `resolve()` (lines ~88–93); `src/houdocs/node/resolver.py` — `_node_document_priority` / `build_node_metadata`.
- **Description:** The resolver computes a `priority` integer for every node document (runtime_resolved +1000, stem match +100, explicit version +10, filename version +5, trailing-dash −20) and stores it inside `metadata_json`. But `resolve()` selects with `ORDER BY node_type LIMIT 1` where `node_type` is the sha256-derived ID — i.e., an arbitrary but stable hash ordering. The priority field is never used in any query.
- **Why it matters:** Versioned node docs (`foo.txt`, `foo::2.0.txt`, etc.) can both resolve to the same canonical runtime type; which document `houdocs node sop/foo` returns is decided by hash lexicographic order, not by relevance/priority. The whole priority mechanism is currently dead weight, which also misleads maintainers.
- **Evidence:** node/repository.py:92–93 `ORDER BY node_type LIMIT 1`; priority defined and written into metadata in resolver.py (`_node_document_priority`), no `json_extract(... priority)` or priority column anywhere in queries (verified by grep).
- **Expected impact:** For canonical names with multiple indexed documents, `node` read returns an effectively random one; behavior flips when document IDs change (e.g., path renames), making it non-reproducible across re-inits.
- **Trigger conditions:** Two or more node documents resolving to the same canonical name (typical for Houdini versioned node docs such as `remesh` vs `remesh::2.0` or legacy dashed filenames).
- **Suggested verification:** Populate a scratch `docs.db` with two node_documents rows sharing `houdini_name = 'Sop/foo'` but different priorities; call `NodeRepository.resolve('Sop/foo')` and observe which row wins versus the priority ordering. Confirm no query references priority.

#### Update — 2026-09-07 09:47 — Base d5e3d02

Verified by the query ordering and a duplicate-canonical repository test. `resolve()` previously sorted opaque SHA-derived `node_type` IDs. It now orders by stored metadata priority descending, with `node_type` as a deterministic tie-breaker. `test_node_repository_resolves_duplicate_canonical_names_by_priority` verifies the higher-priority document is returned. Result: Fixed.

### [Fixed] C3. Per-entry `DELETE FROM search_fts WHERE entry_id = ?` forces a full FTS table scan per delete — O(n²) on first init

- **Severity:** Medium
- **Confidence:** High-confidence
- **Affected file/symbol:** `src/houdocs/search/hybrid.py` — `upsert()` (line 73) and `remove()` (line 182); `src/houdocs/search/store.py` — `search_fts` schema (lines 28–33, `entry_id UNINDEXED`).
- **Description:** fts5 virtual tables have no ordinary rowid index usable for `WHERE entry_id = ?` on an UNINDEXED column, so each per-entry delete before insert is a linear scan of the whole FTS index. During a fresh init (reportedly ~40k sections) this happens once per entry, giving ~n²/2 scanned rows.
- **Why it matters:** First-run `houdocs init` runtime inflates super-linearly with corpus size; the delete is also executed even for brand-new entries where no prior row can exist.
- **Evidence:** store.py:29 declares `entry_id UNINDEXED`; hybrid.py:73 executes the delete unconditionally for every entry inside the per-entry loop of `upsert()`.
- **Expected impact:** Tens of seconds to minutes of pure scan overhead at ~40k entries, growing quadratically; slower re-inits after profile changes too (all entries re-upserted).
- **Trigger conditions:** Any init or profile migration that re-upserts the full corpus into `search_fts`.
- **Suggested verification:** Time `houdocs init` on a synthetic corpus of 5k vs 20k sections and compare scaling; or EXPLAIN QUERY PLAN `DELETE FROM search_fts WHERE entry_id = ?` (shows a full scan). Candidate fixes: track known entry_ids in `search_entries` and skip the delete for new ids, or use an fts5 delete via the contentless/external-content pattern.

#### Update — 2026-09-07 09:49 — Base 2ba458c

Verified by the FTS5 `UNINDEXED entry_id` schema and unconditional delete path. Added `search_fts_rows`, which records each FTS rowid. Reindex and removal now delete mapped rows by rowid; legacy rows without a mapping use the previous scan once and are mapped on reinsert. `test_search_fts_rows_track_entry_rowids_for_reindexing` verifies one current FTS row and its rowid mapping after reindexing. Result: Fixed.

### [Fixed] C4. Interrupted init leaves a stale `search.db`; `houdocs search` then hard-fails on the first stale hit instead of degrading

- **Severity:** Medium
- **Confidence:** Plausible
- **Affected file/symbol:** `src/houdocs/search/service.py` — `DocumentSearchService.search` (per-hit `repository.section(hit.source_id)`); `src/houdocs/search/index.py` — cross-database consistency between docs.db and search.db.
- **Description:** docs.db and search.db are updated in separate phases with no cross-database transaction. If init is interrupted after some documents were re-indexed (new section IDs) but before the search phase completed, search.db still references old section IDs. At query time the service calls `repository.section(source_id)` for each hit and lets `document_section_not_found` (`HouDocsError`) propagate, aborting the entire command.
- **Why it matters:** One stale hit makes the whole search command unusable (exit 1, JSON error) even though most results and the lexical index are fine; there is no self-healing until the user re-runs a full successful init.
- **Evidence:** service.py iterates hits calling `repository.section(...)`, which raises (docs/repository.py:71,75); nothing catches per-hit errors; SearchIndexer only reconciles stale entries during a subsequent successful `index_all`.
- **Expected impact:** After a crash mid-init, `houdocs search <query>` fails wholesale for queries whose top candidates include stale IDs.
- **Trigger conditions:** Process termination between the docs-indexing phase and search-indexing phase of `houdocs init`, followed by any search touching affected documents.
- **Suggested verification:** Run a partial init (kill after docs phase), mutate a document so its section IDs change, then query; observe the whole-command failure. Fix suggestion: skip-and-flag stale hits (and/or filter by `is_current` join) rather than raising.

#### Update — 2026-09-07 09:51 — Base 7dee777

Verified with a stale `SearchHit` whose source ID is absent from the current documents database; the original per-hit lookup raised and aborted the result. `DocumentSearchService.search()` now skips only missing section/document references, retaining other `HouDocsError`s. `test_search_skips_stale_hits_without_aborting_current_results` verifies current hits are returned. Result: Fixed.

### [Fixed] C5. Repository read paths let raw `sqlite3.Error` escape — violates the CLI's single-line-JSON error contract on corrupt/locked databases

- **Expected impact:** Any db corruption, disk-full, or concurrent-access scenario on read commands (search/read/node/python/vex) produces tracebacks and breaks scripting/agent integrations.
- **Trigger conditions:** Corrupt docs.db/search.db, unavailable WAL, or lock contention while running any read command.
- **Suggested verification:** Point `_offline_paths` at a file containing garbage bytes and invoke `houdocs read X` — expect a traceback today; after fix, a JSON `docs_database_error` payload. Alternatively broaden `_invoke` to map `sqlite3.Error` to an error code.

### [Deferred] C8. Connection-per-method with no explicit close — high connection churn and reliance on CPython refcounting

- **Severity:** Low
- **Confidence:** High-confidence
- **Affected file/symbol:** `src/houdocs/docs/repository.py` (all methods), `src/houdocs/node/python/vex repositories`, `src/houdocs/search/*` — pattern `with connect(...) as connection:` everywhere.
- **Description:** `sqlite3.Connection`'s context manager commits/rolls back but does not close. Connections are closed only when CPython refcount-GC collects them. Combined with the per-method connection pattern, `init` opens ~2 connections per document (repository `document_for_path` + `section_ids_for_document`), and `all_sections` opens 2 per document for the whole corpus; `hybrid` opens several more per upsert batch.
- **Why it matters:** On CPython this functionally works but is wasteful (repeated PRAGMA setup per call: `foreign_keys`, `journal_mode=WAL`, `synchronous`), slows init, and is fragile on non-CPython runtimes or under tracemalloc/deferred-GC scenarios; WAL files may linger longer than expected.
- **Evidence:** db/connection.py `connect()` runs 3 PRAGMAs per call; grep shows `with connect(` in every repository method with no `.close()`; docs/repository.py `all_sections` delegates per-document queries (2 queries/connections per doc).
- **Expected impact:** Measurable init slowdown (PRAGMA + open/close per call), heavier file-handle churn; correctness impact only off-CPython.
- **Trigger conditions:** Always; magnified on large corpora (tens of thousands of sections).
- **Suggested verification:** Count `connect()` calls during a synthetic 1k-document init (instrument `db.connection.connect`); time init before/after switching repositories to a shared, explicitly closed connection or `contextlib.closing`.

#### Update — 2026-09-07 09:55 — Base 651ae4d

Confirmed the lifecycle pattern, but a correct fix crosses all repositories and changes connection ownership semantics. No bounded performance measurement or non-CPython failure reproduction is available, so production code was not modified. Result: Deferred.

### [ ] C10. `strict_node_lookup` filename fallback never matches versioned runtime names (`foo-2.0` vs `foo::2.0`)

- **Description:** The port is freed before Houdini is launched; another process may claim it in the window, making the openport startup script fail or bind the wrong listener, which surfaces as `houdini_startup_timeout` after the full 30s.
- **Why it matters:** Rare spurious init failures that are hard to attribute; error message does not mention the possible port collision.
- **Evidence:** Standard bind/close/reuse pattern in `_unused_loopback_port`; the probe poll loop cannot distinguish "port stolen" from "Houdini slow".
- **Expected impact:** Occasional 30-second timeout instead of a fast, explanatory failure.
- **Trigger conditions:** Another process binds the probed port between `_unused_loopback_port()` returning and `houdini` opening its command port.
- **Suggested verification:** Hold the chosen port with a helper socket between selection and launch in a test; observe timeout. Retry-with-new-port logic would eliminate it.
