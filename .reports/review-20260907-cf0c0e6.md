## High-confidence candidates

### [Fixed] C1. Dense vector writes and search-entry writes are separate transactions; orphans degrade KNN recall
- **Severity**: Medium
- **Confidence**: High
- **Affected**: `src/houdocs/search/hybrid.py:62-90` (`upsert`), `src/houdocs/search/dense.py` (KNN `LIMIT k`)
- **Description**: `HybridSearchBackend.upsert` writes vectors via `self.dense.upsert(profile, group, vectors)` (hybrid.py:82) in one connection/transaction, then writes `search_entries`/`search_content`/FTS rows in a second transaction. A crash or `sqlite3.Error` between the two leaves vector rows for entry IDs that have no current `search_entries` row.
- **Why**: The two stores are not updated atomically. `remove()` only cleans vectors for entry IDs it is told about; an entry whose vector was written but whose row write failed is never re-removed unless the same entry ID is later upserted or explicitly removed.
- **Evidence**: hybrid.py:76-90 — dense upsert loop precedes the entries transaction; separate `with connect(...)` blocks. dense KNN search applies `LIMIT k` (dense.py, `search`) regardless of entry currency; `_load_entries` (hybrid.py:331) then filters `is_current=1` after the limit.
- **Impact**: Orphan/stale vector rows consume the KNN `k` budget before currency filtering, silently reducing dense recall — in the worst case dense returns zero live candidates. Self-heals only if the same entries are re-upserted.
- **Trigger conditions**: Process crash, disk-full, or `sqlite3.Error` during the entries transaction after a successful dense upsert; repeated across indexing runs the orphan set can accumulate.
- **Verification direction**: Unit test that monkeypatches the entries-transaction connection to raise after `dense.upsert` succeeds, then asserts `search()` recall; or query `search_vec_*` for entry IDs absent from `search_entries` after a forced mid-upsert failure. Consider a maintenance sweep deleting vector rows whose entry IDs are not current.

#### Update — 2026-09-08 06:08 — Base 832b79f
Verified by code-path inspection: `dense.upsert()` committed before the separate entries transaction, so a later entry-write failure left vector rows orphaned. Moved production `SQLiteVecIndex` upserts and profile-move removals into the entries transaction, and added a forced entry-write failure regression test that confirms both vector-profile and entry rows roll back. Result: Fixed.

### [Fixed] C3. Lexical search swallows `sqlite3.OperationalError` and returns empty results
- **Severity**: Medium
- **Confidence**: High
- **Affected**: `src/houdocs/search/lexical.py:43-44`
- **Description**: `SQLiteFtsIndex.search` catches `sqlite3.OperationalError` and returns `[]`, conflating "no matches" with real failures (corrupt FTS index, locked database, malformed query expansion).
- **Why**: Operational errors are environmental and should propagate (or at least be logged/reported); the current catch makes every infrastructure failure look like an empty result set.
- **Evidence**: lexical.py:43 `except sqlite3.OperationalError:` immediately followed by an empty-list return inside the query method.
- **Impact**: Silent wrong answers (`search` returns fewer/no hits with exit 0); users cannot distinguish a healthy no-match from a broken index. Under WAL + short-lived connections the lock case is rare, which makes the masking harder to notice in production.
- **Trigger conditions**: FTS index corruption, `database is locked` contention, or any OperationalError raised by the MATCH query.
- **Verification direction**: Test injecting an OperationalError (e.g., drop the FTS table mid-test) and assert an error/exception rather than `[]`; narrow the catch to the specific "no such table" cold-start case if that was the intent, and only when the index is expected to be absent.

#### Update — 2026-09-08 06:18 — Base 1e03905
Removed the blanket `except sqlite3.OperationalError: return []` in `lexical.py:40-44`; `SQLiteFtsIndex.search` now lets all database-level errors propagate. Added `test_fts_operational_error_propagates` confirming that a query-time `sqlite3.OperationalError` raises rather than returning `[]`. Result: Fixed.
